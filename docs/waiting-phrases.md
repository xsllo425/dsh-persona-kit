## 一、许可结论（能用到什么程度）

### A 库：三层许可，文字能用，写法要守规矩

`LICENSE.md` 把仓库切成三块：

1. **原创程序与维护脚本：MIT**（`LICENSE.md` L3–L23）。跟文案无关。
2. **本仓库新写的研究说明和提示词：CC BY 4.0**（`LICENSE.md` L25–L28），署名要求写的是「HABAI182 / AI Girls Atlas」+ 许可链接 `https://creativecommons.org/licenses/by/4.0/`。
   → `community-impressions.md`、`encyclopedia/personas/*.md`、`encyclopedia/memes/*.md`、`docs/` 里的分析文字，都属于这一档。
3. **第三方角色、图像、视频、声音、商标：不适用以上统一许可**（`LICENSE.md` L32–L36），逐文件见 `THIRD_PARTY_NOTICES.md`、`data/assets.json`、`docs/06-rights-and-provenance.md`。DeepSeek 鲸鱼娘另保留「上善无形 → ZipZipPipe」署名链和 CC BY-NC-SA 4.0 声明。

关键的一条限制在 `LICENSE.md` L30：CC BY 4.0 **只覆盖维护者新写的说明与分析，不把其中引用或链接的第三方作品重新授权**。也就是说：

- **可以**：读它的概括、按梗重写成自己的句子 → 属于 CC BY 4.0 允许的改编，需署名 + 标改动。
- **要标注**：如果某条文案几乎照搬它的原句，就必须在第三方声明里写「HABAI182 / AI Girls Atlas，CC BY 4.0，附链接，改动说明」。
- **不可以**：直接抄条目里引用的 B 站评论、视频字幕、论坛楼层原句。那些是第三方内容，版权归原发言者/作者，A 库自己也没拿到再授权（条目里已用「单条评论 / 单作者作品 / 视频字幕」标了范围）。
- **不可以**：用任何图片。A 库图片是 CC BY-NC-SA 4.0 或各作者的开放分享声明，NC 与「相同方式共享」都跟本插件 MIT 冲突。

按 `docs/06-rights-and-provenance.md` L41–L52 给的署名模板，引用时的写法是：角色原型 + 二次设计作者 + 原帖 + 许可 + 本次改动。落到本仓库，就是新开一节进 `THIRD_PARTY_NOTICES.md`。

### B 库：只能看，不能抄

- `LICENSE` L5–L10：许可只覆盖**本仓库作者的补全工作**（`设定图/`、`scripts/` 下的成品与提示词、生成记录、`README.md`、`版权与授权.md`、`docs/`），协议是 **CC BY-NC-SA 4.0**（署名 + 非商业 + 相同方式共享）。
- `LICENSE` L12–L14：`参考原图/` 不在许可范围内；第 12 条 Q 版冬装（冬装小肥鱼 / 冬装小肥鱼2）来源作者未标注、授权 `unknown`。
- 角色形象与原始设定版权归 **ZipZipPipe**（`版权与授权.md` L3–L10），B 库自己是「非商业二次创作，不得商用，转载请保留原作者署名」。

结论：**NC（禁商用）+ SA（同协议共享）跟本插件的 MIT 直接冲突，B 库的文字与图片一个字/一张都不要搬进仓库分发物。** 好在它本来也没有梗，这条只是把边界钉死。

### 一句话总结

> 能做的只有一件事：**按梗重写**。
> A 库允许「读懂 → 用自己的话写 → 署名」，禁止照抄它引用的社区原始发言；B 库连参考文字的资格都没有，只能当看图用的视觉参考。两个库的图片一律不进插件。

### 不确定的两处

- `community-impressions.md` 里那些「**类型 · 说明。**」加粗小标题，是本库编者的概括（CC BY 4.0），但它下面挂的出处链接指向第三方。我按「概括可改写、原句不可抄」处理，这是推断而非原文明示——原文没有逐条区分。
- A 库的 `docs/` 与 `encyclopedia/` 是否**全部**算「新写的研究说明」，`LICENSE.md` 只写了类别没列文件清单。本文件引用的都是明确属于分析/说明性质的文字，未引用任何 JSON 元数据或第三方字段，风险最低，但仍属推断。

## 二、候选文案分组清单

**格式说明**：每条给「文案 / 出处 / 性质」。性质分三档，**不要混着用**：

- **本库原创** = A 库编者的创作草案（`personas/*.md` 的八维度表、`dialogue-comparison.md` 的 117 句）。**不是社区梗**，没有群众基础，但也没有版权与冒犯风险。

长度按 8–20 字控制，句式对齐现有的「正在理解用户发送的不可见 token…」。

### 二·0 复用价值速判（先看这段再看清单）

同一行「正在…」会在一次会话里出现几十次，**重复感是最大的敌人**。所以判断标准不是「这条好不好笑」，而是「第 30 次看到还笑不笑」。

| 档 | 判断 | 处理 |
| --- | --- | --- |
| **长效** | 不依赖具体时间、具体作品、具体名次；换个会话、换个月还能接上 | 可以进默认轮换池 |
| **看情况** | 依赖角色当前状态（正在摸鱼、正在被夸），只在特定模式/强度档下出现才合理 | 只在「贱萌/大肥鱼」档或长等待时用 |
| **一次性** | 靠某个具体事件成立（某次投票名次、某个具体视频、某次活动） | 不进池子，见第三节 |

**长效梗（跨会话还会笑）**：白饭/饭碗/token 投喂、摸鱼转包、「被叫大肥鱼先嘴硬」、免责声明与格式大师、大小姐、哈基米猫猫、豆包说人话、逐层拆条件、先通读再落笔。

## 四、还需要拍板的问题

1. **「大肥鱼」这个词要不要进默认文案？**
   它是社区声量最大的一条（4 个独立来源），但把「胖」写进产品 UI 有歧义：可能是角色自嘲，也可能被读成在说用户。而且插件现有设定是「别人说你胖才要抗议」。建议只用**角色自嘲**的写法（B7「正在嘴硬说不是胖」），不用直呼式（E2）。

2. **带真实公司影子的梗，一条都不要，还是留「无恶意」那几条？**
   我建议一刀切：**不出现任何公司名、不出现「降智/跑分/刷榜」这类能力贬损词**。代价是技术向文案只能从 A 组（本库原创人设）里出，会少一点「圈内人才懂」的笑。你如果同意，我就按这个口径过一遍。

3. **「摸鱼 / 转包」这类「她没在干活」的梗，放进「正在…」会不会被读成卡住了？**
   等待行本来就容易被怀疑「是不是死了」，再来一句「正在假装没摸鱼」，反感风险不低。建议：只在「贱萌 / 大肥鱼」强度档，或等待超过 30 秒时才出这类文案，正常档不出。

4. **角色专属文案是否跟随当前角色切换？**
   现在有 5 个预设角色、各有五档强度。两种做法：① 全局一套通用池（A/B/C/E 组）；② 跟随当前 `role`，再叠加通用池。要做 ② 才用得上 D 组的 25 条，也才需要给新角色补文案的规范。

5. **「token」这个词能不能出现在 UI 里？**
   B4 / B10 / B11 都用到。部分用户对这个词无感甚至反感（觉得太技术、显得在算计成本）。可以整体换成「饭」。需要你定。

6. **出处署名写在哪、要不要中英双语？**
   仓库约定是「新增第三方资产要在 `THIRD_PARTY_NOTICES.md` 登记」，我建议在那里新开一节写 A 库（HABAI182 / AI Girls Atlas，CC BY 4.0，链接 + 改动说明）。另外约定还写着「发给模型的所有文字走 `lib/lang.js` 的 i18n，新增用户可见文案必须中英双语」——但等待行是**宿主 UI**、不是模型文字，要不要也走 i18n 得先确认接入点（TODO 第 3 条没查）。
